## 11. Durable WorkItemJob schema

WorkItemJob has a GUID primary key and stores SourceId, stable ExternalWorkItemId, readable WorkItemReference, Title, stable ExternalAssigneeId, internal AgentId, Status, nullable CurrentAttemptId, SourceUpdatedAt, CreatedAt, and UpdatedAt. The unique identity is (SourceId, ExternalWorkItemId). Status values are Queued, Running, Blocked, AwaitingReview, and Completed. Agent-to-job deletion is restrictive. There is no external URL, description, lease, checkpoint, error, or retry metadata on the job. CurrentAttemptId fences worker updates against an obsolete attempt; it is not a foreign key from job to attempt.

The queued record is a compact durable work pointer and display snapshot. WorkItemExecutionAttempt is a separate EF entity with Id, WorkItemJobId, CreatedAt (claim time), nullable StartedAt and FinishedAt, ProviderId, ProviderSessionId, TaskSnapshot, TaskSourceUpdatedAt, WorkingDirectory, and nullable enum StopReason stored as a string. Provider, session, input, and workspace fields remain null on claim. The existing execution worker saves the latest ticket snapshot, source revision, provider ID, workspace, and start time before invoking a provider. WorkItemExecutionAttempt now additionally stores nullable Phase (Planning or PlanningComplete, persisted as a string), PlanningInputJson, PlanningResultJson, and PlanningCompletedAt. Existing attempts retain null phase; no default misclassifies old attempts. Planning checkpoint completion leaves FinishedAt null even when the job is Blocked. See section 19 for the checkpoint semantics. A separate `CheckpointReference` and `ProviderCheckpoint` abstraction were deliberately removed: no adapter yet stores external conversation state behind such a reference. `ProviderSessionId` may be null for an adapter without provider-managed sessions.

## 16. Persistent-service and reliability decisions

The --sync command invokes WorkItemSynchronizer once. It resolves a discovered assignee through (SourceId, ExternalUserId), rejects unmapped or inactive agents, creates a Queued job if absent, and updates mutable title/reference snapshots only when the provider timestamp is newer. It never changes an existing job status. It reports New, AlreadyQueued, Updated, Unmapped, AgentInactive, AssignmentChanged, or Unchanged. A changed external assignment is flagged instead of silently moving an existing job. A completed job is not reopened by a newer ticket snapshot; reopening/retry semantics remain undecided.

The first local --sync created one queued job for STEPI-18, mapped to team-lead. The second run returned AlreadyQueued; the user confirmed the single durable row in HeidiSQL. --sync performs no AI invocation and no YouTrack writes. Sequential idempotency is verified. Concurrent synchronizers can still race at insertion; the unique index prevents duplicate rows, but conflict handling belongs with later service reliability work.

The xUnit test project uses SQLite in memory and fake discovery, readers, providers, and process clients. Four sync tests cover repeat runs, newer snapshots preserving Completed status, unmapped/inactive agents, and changed external assignment. YouTrack tests cover pagination and the full read. WorkItemExecutionWorkerTests cover changed assignee, committed snapshot before provider invocation, session retained on a usage-limit stop, and cancellation leaving Running. CodexSessionTests cover callback ordering, prompt child termination on callback failure, continuation prompt delivery, and session-ID checks; four targeted tests passed. RepositoryAccessServiceTests verifies the Read/Write model, deny by default, source filtering, and inactive agent filtering. Tests used EnsureCreated for the model; the new migration was separately exercised on a disposable database. The assistant inspected the remote source but did not rerun Windows tests.

WorkItemClaimService.ClaimNextAsync uses EF Core in a short serializable transaction. It selects one Queued job for an enabled, non-deletion-requested agent only when that agent's count of Running jobs is below MaxConcurrentJobs; it conditionally updates the job to Running, sets CurrentAttemptId, inserts a WorkItemExecutionAttempt, and commits. One call returns one WorkItemClaim or null. Repeated calls can fill multiple slots for the same assigned agent; a worker instance does not reassign the job to another agent. It orders candidates by SourceId and stable ExternalWorkItemId because SQLite EF cannot order the existing DateTimeOffset CreatedAt property. This is deterministic, not FIFO. No direct SQLite SQL is embedded in the service. A provider change still requires a concurrency review and tests, including transaction-conflict handling.

The focused WorkItemClaimServiceTests runs concurrent claimers against a temporary SQLite file with MaxConcurrentJobs = 2 and three queued jobs. It verifies two distinct jobs and attempts become Running, one remains Queued, and another claim returns null. The first five migrations were individually confirmed operational earlier; the user subsequently reported all seven applied. The assistant has not queried the live migration history. No production command or hosted service invokes ClaimNextAsync, so the real STEPI-18 job should still be queued; do not claim it manually until execution and recovery are ready. A claim has no automatic lease or expiry. A crash can leave a Running job requiring reconciliation.

WorkItemExecutionWorker.RunNextAsync is the concrete caller of ClaimNextAsync in tests and is registered in DI, but is not hosted. It validates working directory, reads the latest full ticket by source and stable ID, checks identity, assignee, and required state, and saves TaskSnapshot, source revision, provider ID, workspace, and StartedAt before invoking IWorkItemExecutionProvider. The provider's session callback saves ProviderSessionId immediately through a guarded update. Every attempt write is fenced by the job's CurrentAttemptId and Running status; final job/attempt updates share a short serializable transaction. Changed state/assignee/identity or ticket-read failure becomes Blocked with a typed StopReason. ## 20. Agreed target service workflow and upcoming milestones

The owner confirmed the intended service workflow on 2026-10-05. This section describes the target behavior; the coverage table distinguishes it from today's implementation. Individual implementation milestones still require scope agreement and the review workflow in section 2.

### Startup and continuous operation

1. Report retained unresolved operational issues from the previous run without changing their history or claiming that they are still current.
2. Validate configuration and observe the configured work-source connections/projects, Git repositories, and execution-provider capabilities. Check a shared connection once and its projects separately. Evaluate capabilities required by each operation; authentication, project visibility, issue reads, local workspace writes, and remote push are distinct. Failures should affect dependent work, while unrelated configured work remains eligible.
3. Reconcile jobs stored as Running before taking ownership or resuming them. A database row is not proof of a live process. Establish exclusive host/process ownership, observe existing children, and verify the current attempt, ticket identity/assignment/state/content, saved input/session, permissions, and workspace/branch/HEAD. Do not take over a still-live process or silently start a new session when the saved one is unusable.
4. Resume eligible interrupted work and admit eligible queued work within each agent's MaxConcurrentJobs. Resume priority does not mean waiting for every Running job to finish before starting queued jobs; free capacity can serve other eligible work.
5. Discover ready external work independently of long-running execution and synchronize it into the durable queue. Keep status-preserving synchronization: ticket changes do not automatically reopen Blocked or completed jobs. Startup reconciliation precedes execution admission; discovery remains an independent correctness loop.
6. Observe operation results, report failures/recovery, monitor active processes and relevant permission changes, and apply the agreed stop/retry policy. Preserve durable snapshots, sessions, workspace changes, and immutable completed planning results.

### When to check dependencies

Use startup probes, checks before relevant operations, and observations from actual operation outcomes. Do not probe every dependency at every discovery interval. Discovery requests themselves establish discovery availability; explicit project checks cover a different capability that an empty discovery response cannot establish. Git read success does not establish push permission.

Before starting, resuming, or crossing a phase boundary, evaluate the capabilities that operation requires using fresh enough observations and current Traily grants. Define freshness, Unknown handling, bounded retries, and backoff in the relevant milestone; no numerical policy has been agreed. Failed dependencies need periodic recovery checks, and healthy dependencies may need periodic probes where actual operations do not provide sufficient evidence. Keep provider calls outside long database transactions and polling independent of execution.

Record dependency availability in scoped observations/operational issues. Readiness decides whether a particular job may proceed; an unresolved historical issue alone is not a complete readiness decision. Stop admitting affected work when its required capabilities are not sufficiently verified. For active work, distinguish transient outages/rate limits from revoked grants, disabled agents, and invalidated input. Whether to retry, pause at a checkpoint, or cancel immediately remains policy to agree before implementation. Changing job status alone does not stop an agent process.

Planning is a phase of a work-item attempt, not a separate job with an Unavailable status. Blocked belongs to the job and has a retained stop reason; capability availability belongs to observations. Dependency recovery permits re-evaluation but does not automatically reopen a Blocked job or overwrite its saved planning result. Live process enforcement and eligible retry transitions must preserve this distinction.

6. **Retry transitions.** Define eligibility and limits, session continuation versus a fresh attempt, input/ticket revalidation, concurrency slots, and immutable completed planning history. Do not automatically reopen jobs merely because a connection recovers.
7. **Exclusive execution ownership and startup reconciliation.** Establish single-host ownership, identify live/orphan processes, reconcile Running attempts, and construct explicit continuation guidance. ### Execution and recovery constraints to preserve

The worker currently claims, revalidates, snapshots, and invokes a provider only when called in tests; polling does not call it. The planning checkpoint is also tested and registered but has no production caller. Startup visibility of unresolved operational issues is complete; expand specific configuration/access detection and readiness incrementally before agreeing active-run permission/cancellation policy. Retry transitions follow as a separate execution milestone before safe dispatch. Evolve this into claim → read-only planning → selected repository/access check → per-repository workspace preparation → implementation → review, with durable phase transitions. One agent may legitimately modify multiple repositories for a single ticket (for example StepIn API and UI, or a DevOps change); do not assume specialist agents or one repository per job. The agent can inspect only permitted Read repositories; if a hidden repository is never mentioned in ticket or visible code, it cannot reliably discover it. A no-row access grant is denied. A read-only local preflight is useful after planning chooses targets but does not prove remote connectivity or push authorization.

Codex process callback failures now stop the child promptly, and an explicit session resume path with same-ID checks exists at the adapter layer. There is no hosted provider process supervisor, operational resume caller, exclusive host lock, or orphan reconciliation yet. Directly observe active tasks/processes, reconcile on startup, and use periodic backstop without taking over a still-live old host/child. A usage-limit result is Blocked with retained session/snapshot; cancellation leaves Running; a crash can do the same. Resume only after verifying session, workspace, Git branch/HEAD, ticket assignment/stage/content, and saved input. A continuation prompt is new guidance based on observed state, not the original instructions resent. If a session is absent or unusable, do not silently start over. The owner controls merges, releases, permissions, and final acceptance.
